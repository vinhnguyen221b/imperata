# Starter kit guide

These files are **examples**, not a validated agent harness installation. `imperata-kit.mjs` installs them into an **authorized** repository and keeps them up to date (`KIT_GUIDE.md` in the kit's repository); review what it adds before the first run.

0. Fill in `.orchestra/project.md`: the product, where its sources are, stack rules, security-sensitive areas and what each specialist must cover. Every agent reads it first; the kit names no product.
1. Select **Copilot harness** in VS Code. Use the Agent Customizations editor to verify the six specialist agents and Orchestrator appear (only Orchestrator is user-invocable by default), and type `/imperata` in the chat to see the eight commands that start each step of a run (`/imperata-start <feature>` and the others).
2. Check each agent's tool inventory; Copilot uses native delegation and role frontmatter names are case-sensitive. Each agent also names a `model`: `claude-opus-5.5` for the Architect and the Code Reviewer, `claude-sonnet-5.5` for the Orchestrator, the Business Analyst, the UX Designer, the Developer and the QA Engineer. That is the default for the role and follows the cost guidance of the blueprint (its document 07, "Cost awareness", in the kit's repository). For the Developer and the QA Engineer the Orchestrator asks for a model per task from the task's `Complexity` in the plan (`low` → `claude-haiku-5.5`, `standard` → `claude-sonnet-5.5`, `high` → `claude-opus-5.5`) and lists each delegation in the "Model per task" table of `delivery.md`. These identifiers are **unconfirmed**: the VS Code reference shows no concrete model ID and says to use the identifiers that editor completions insert for the Copilot harness. Open each agent file, trigger completion on `model`, and replace the value with an identifier your plan offers. The value is a single string on purpose; VS Code also accepts a list, but Copilot CLI was reported to reject one.
3. `cp .orchestra/examples/copilot-cli.mcp.example.json .mcp.json` only if the portable Copilot format and Playwright MCP are allowed. Alternatively use the VS Code format (`.vscode/mcp.example.json`); don't deploy both without understanding their effects. Confirm server actually starts. The sample pins a version of the server; change it only to a version you have tried.
4. Run `node scripts/validate-gates.mjs .orchestra/runs/EXAMPLE.run.json` from repo root to check the sample manifest (it carries `approvalMode` and `approvals`). It does **not** report delivery readiness. `.orchestra/` holds what the kit and the project set up (the schema, the templates, the rules for tests, the project profile, this sample), never a run; a real run keeps its manifest and artifacts in `sdlc/runs/<runId>/` (`run.json`, `input.md` and the rest), and the validator is then pointed at that `run.json`.
4a. Run `node scripts/render-run-board.mjs` from the repo root and open `sdlc/board.html` in a browser. With no run yet the page is empty; during a run it shows every run's gates, who has the next move, the open questions as cards whose choices build your reply to the Orchestrator, blockers, task waves and traceability. Each run also gets `sdlc/runs/<runId>/board.md`, the same as Mermaid diagrams for GitHub. `sdlc/board.html` is not committed (the kit adds it to `.gitignore`); commit the `board.md` files with the run. Copilot has no hook to re-render it: the Orchestrator renders it after each change, and you can at any time. For a live board, run `node scripts/board-server.mjs` in a terminal of your own and open `http://127.0.0.1:4319/sdlc/board.html`: it refreshes when the run changes, and its "Send to Orchestrator" button saves your decisions in the run's `decisions/` folder, so you only tell the Orchestrator "decisions sent". When a gate is yours (specification, plan, delivery), an approval card names the documents to read, opens them as readable pages, and sends your Approve or Request changes for the exact version you read. The server listens on 127.0.0.1 only and needs the token in the page to accept a decision. With `--auto-run copilot` it also starts the Orchestrator through Copilot CLI after each Send (`copilot -p … --agent sdlc-orchestrator --no-ask-user`), allowed the tools in `.orchestra/auto-run.json`. Allow rules in your own Copilot settings apply to that session as well, and nobody is there to approve what they allow, so keep them narrow. Copilot CLI has no budget flag, so nothing caps the cost of a session. This path was written from the Copilot CLI documentation and has not been run: check that `--agent sdlc-orchestrator` finds `.github/agents/sdlc-orchestrator.agent.md` and that `write(sdlc/**)` limits writes as intended before relying on it. Copilot Chat in VS Code offers no supported way to start a prompt from outside the editor.
5. Choose the approval mode for the pilot. `local-record` needs nothing more. `pull-request` needs a GitHub remote, the `gh` CLI signed in, and your explicit permission for the Orchestrator to push branches and open pull requests; the Orchestrator never merges. Protect the main branch so that only a person can merge.
6. For `pull-request` mode, rename `.github/workflows/pr-checks.yml.example` to `pr-checks.yml`, replace the commands marked REPLACE with the repository's real ones, and make both jobs required checks. Treat its first run in your repository as part of the pilot. The validator's call in that file names the job "Build and test" with `--require-check`, so a delivery pull request on which that job was skipped does not pass; if you rename the job, rename it there too.
7. Run artifacts follow `.orchestra/templates/`. For each stack that really exists in the repo, create one stack skill from `.orchestra/templates/stack-skill/` in the skills folder of each agent tool the repository uses (`.claude/skills/<stack-name>/` for Claude Code, `.github/skills/<stack-name>/` for Copilot), or let the first plan do it: when no skill exists, the Architect plans a `TASK-00` that writes it, and you approve its conventions with the plan. Do not create skills for stacks that are not there.
8. Spec Kit is not part of a run. Where it is installed (`.claude/skills/speckit-*` for Claude Code, `.github/skills/speckit-*` for Copilot), the Orchestrator uses none of its skills, scripts or `specs/` folder, and the project's rules are in `.orchestra/project.md`, not in Spec Kit's constitution. A specification or a plan written with Spec Kit's commands outside a run is decided where no gate of the kit sees it.
9. Adapt agent prompts to your actual repo/package commands and your organization's policy; only then enable external writes.

## Never assume

- Sample `run.json` means a real ticket, PR or test existed.
- A green step on the run board means the gate passed. It means the manifest says `PASSED`; the board reads artifacts and checks nothing outside the repository.
- Tool names in frontmatter guarantee the actual session has those tools.
- A `model` in frontmatter is the model that ran. With the default `model-policy: preferred` an identifier that is not available does not block the agent. In VS Code, the Orchestrator's session runs on the model selected in the chat's model picker, not on the one its file names: select that model before you send a command. The VS Code reference says that selecting an agent sets the picker to the first available model of its file, and that a model you select yourself stays for the conversation; that was read, not tried. Which one is yours to choose, and it is most of what a run costs. The Orchestrator's file names `claude-sonnet-5.5`. A specialist called through the `task` tool runs on the model of its own file, which can differ from the model of the session. Check the model shown for each delegated step in your first run.
- The Orchestrator can set a model per task under Copilot. Copilot's `task` tool takes a model argument, but by the Orchestrator's own account a rule of Copilot's lets it set a model only when the user names one. Left to itself it sets none: every task runs on the specialist's own model, and the table in `delivery.md` says so (`NOT_SELECTED`). So the implement command names the model of each task for you, by the Orchestrator's table, and the verify command names the model of the whole suite, at `standard`. With the model named, the Orchestrator passes one with every delegation of a task, and Copilot's record names that argument as the source of the model that runs. The tool does not show the Orchestrator which model ran, so the "Model per task" table reads `NOT_CONFIRMED`. A `Complexity` rating is the Architect's judgement, approved with the plan. `scripts/validate-gates.mjs` checks that every `### TASK-NN` section of the plan has one with a reason; it does not check that the level is right. It also checks that the "Model per task" table in `delivery.md` is filled in, names tasks of the plan and never runs a task below the plan's level. That table is the Orchestrator's own record: the validator cannot tell which model really ran or whether a delegation was left out.
- Playwright MCP proves regression without deterministic tests and an executed report.
- An LLM instruction prevents access to unauthorized files/services.
- The QA agent's "test files only" rule is enforced. Its `edit` tool is workspace-wide; the Orchestrator's git check afterwards detects a violation, it does not prevent one.
- A gate set to `PASSED` in `run.json` was set by the right person. In `local-record` mode the validator checks that a record exists, not who wrote it. In `pull-request` mode with `--verify-remote` it checks who merged, which is as strong as the branch protection on the repository and no stronger.
- A pull request merged by the same account that opened it is an independent approval. In a personal pilot the Orchestrator works under your account, so author and merger are the same; the validator warns about this and does not fail.
- `--verify-remote` has been proven against GitHub. The kit's tests run it against a stand-in for the `gh` CLI only.
- A personal Copilot session has the same entitlements as one under an organization's plan.
- An agent cannot run a command such as `/imperata-merge` by itself under Copilot. Each command sets `disable-model-invocation: true`, which the VS Code documentation says limits it to the slash command; that has been tried in Claude Code only.
